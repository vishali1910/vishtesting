Fundamentals
Core QA concepts every tester must know cold
Q01
What is software testing and why is it important?
BasicConcept
▾

Software testing is the process of evaluating a software application to identify differences between expected and actual behavior, and to verify that it meets the specified requirements. It ensures the product is bug-free, reliable, and delivers value to the end user.

Detects defects early — fixing bugs in production costs 10x more than fixing them in development
Ensures quality, security, and performance before release
Builds confidence in the product for stakeholders and end users
Prevents financial and reputational damage from failures
💡 Real-World Example
An e-commerce site launches without testing its checkout flow. Users can't complete purchases during a sale — the company loses $200K in an hour. If testing had been done, the bug would have been caught for $50 in developer time.
Q02
What is the difference between Quality Assurance (QA) and Quality Control (QC)?
BasicConcept
▾

QA (Quality Assurance) is process-oriented — it focuses on preventing defects by improving development processes. QC (Quality Control) is product-oriented — it focuses on finding defects in the finished product.

AspectQAQC
FocusProcessProduct
GoalPrevent defectsFind defects
WhenThroughout SDLCAfter development
WhoEntire teamTest team
ExampleWriting coding standardsExecuting test cases
Q03
What is Verification vs Validation? Explain with examples.
BasicConcept
▾

Verification asks: "Are we building the product right?" — It checks documents, designs, and code without executing it. Validation asks: "Are we building the right product?" — It runs the actual software to check it meets user needs.

💡 Example
Verification: Reviewing the login page's design spec to confirm it includes a "forgot password" link before coding begins.

Validation: Actually running the app and clicking "forgot password" to see if the reset email arrives correctly.
Verification = static testing (reviews, walkthroughs, inspections)
Validation = dynamic testing (actually running the software)
Q04
What are the 7 Principles of Software Testing?
Intermediate
▾
Testing shows presence of defects — Testing can prove bugs exist, but never prove software is 100% bug-free.
Exhaustive testing is impossible — You can't test every possible input/scenario; prioritize by risk.
Early testing saves money — The earlier a bug is found, the cheaper it is to fix.
Defect clustering — 80% of defects are found in 20% of modules (Pareto Principle).
Pesticide paradox — Running the same tests repeatedly stops finding new bugs; update your test suite regularly.
Testing is context-dependent — A banking app needs different testing than a gaming app.
Absence of errors fallacy — A bug-free app that doesn't meet user needs is still a failure.
Q05
What is a Test Plan? What does it contain?
Basic
▾

A Test Plan is a formal document that describes the scope, approach, resources, and schedule for a testing effort. It serves as a blueprint for the entire testing process.

Scope: What will and won't be tested
Objectives: Goals of the testing effort
Test strategy: Approach, types of testing, tools
Resources: Team members, environments, tools needed
Schedule: Timelines, milestones, deadlines
Entry/Exit criteria: When testing starts and ends
Risk & mitigation: Known risks and contingency plans
Q06
What is the difference between a Test Case and a Test Scenario?
Basic
▾

A Test Scenario is a high-level description of what to test. A Test Case is a detailed, step-by-step description of how to test a specific scenario with exact inputs and expected results.

💡 Example — Login Feature
Test Scenario: Verify that the login functionality works correctly.

Test Case 1:
Steps: 1) Open login page 2) Enter valid email user@test.com 3) Enter valid password Pass@123 4) Click Login
Expected Result: User is redirected to the dashboard.

Test Case 2:
Steps: 1) Open login page 2) Enter invalid email wrong@x.com 3) Enter any password 4) Click Login
Expected Result: Error message "Invalid credentials" is displayed.
Q07
What are Entry and Exit Criteria in testing?
Intermediate
▾

Entry Criteria are conditions that must be met before testing starts. Exit Criteria are conditions that must be met before testing ends and the product is declared ready for release.

Entry Criteria (to START testing)Exit Criteria (to STOP testing)
Requirements are finalized & approvedAll planned test cases executed
Test environment is readyNo critical/high bugs open
Test data is preparedPass rate ≥ 95%
Build is deployed & stableTest coverage goals met
Q08
What is a Requirements Traceability Matrix (RTM)?
Intermediate
▾

An RTM is a document that maps every requirement to its corresponding test cases, ensuring complete test coverage and that no requirement is left untested.

💡 Example RTM
REQ-001: User can log in → TC01, TC02, TC03
REQ-002: Password reset via email → TC04, TC05
REQ-003: Remember me for 30 days → TC06

If REQ-003 has no test cases, the RTM reveals this gap immediately.
Q09
What is Risk-Based Testing?
Intermediate
▾

Risk-Based Testing prioritizes test cases based on the likelihood and impact of failures. High-risk areas get tested first and most thoroughly. This is crucial when time is limited.

Risk = Probability of failure × Impact of failure
Payment processing (high risk) → test extensively first
About Us page (low risk) → test minimally or last
💡 Example
For a banking app, you'd prioritize: fund transfer, account login, and balance display (high risk, high impact) over UI color themes and footer links (low risk, low impact).
Q10
What is Test Coverage vs Code Coverage?
Intermediate
▾

Test Coverage measures how much of the requirements or features are covered by tests. Code Coverage measures how much of the actual source code is executed during testing.

💡 Example
Test Coverage: If 40 out of 50 requirements have test cases → 80% test coverage.

Code Coverage: If tests execute 800 out of 1000 lines of code → 80% code coverage.

Tools for code coverage: JaCoCo (Java), Istanbul/NYC (JS), Coverage.py (Python)
Q11
What is Shift-Left Testing?
Intermediate
▾

Shift-Left Testing means moving testing activities earlier in the development lifecycle — to the left on the project timeline. Instead of testing only after code is written, you test during requirements, design, and development phases.

Review requirements before coding starts (catches ambiguity early)
Developers write unit tests alongside code (TDD)
QA reviews design documents, not just the final product
Result: Bugs are 10–100x cheaper to fix
Q12
What is a Test Environment and what are the common types?
Basic
▾

A Test Environment is the combination of hardware, software, network configuration, and data used to execute tests. It should closely mirror the production environment.

DEV: Developer's local machine — first line of testing
SIT (System Integration Test): All modules integrated and tested together
UAT (User Acceptance Test): Business users validate the system
Staging/Pre-prod: Mirror of production — final check before release
Production: The live environment — monitored post-release

Software Development & Testing Life Cycle questions
Q01
What is SDLC vs STLC? Explain the phases of each.

▾

SDLC (Software Development Life Cycle) is the entire process of building software. STLC (Software Testing Life Cycle) is the testing subset within SDLC.

SDLC PhasesSTLC Phases

3. Implementation (coding)3. Test case development

5. Deployment5. Test execution

Q02
What is the Waterfall model? Pros and cons?
Basic
▾

The Waterfall model is a linear, sequential approach where each phase must be completed before the next begins. Like a waterfall, you can't flow backwards.

💡 Flow
Requirements → Design → Coding → Testing → Deployment → Maintenance

Each phase produces a deliverable before the next phase begins.
✅ Simple, easy to understand and manage
✅ Works well for projects with clear, fixed requirements
❌ Testing happens late — bugs found are expensive to fix
❌ No flexibility for changing requirements mid-project
Q03
What is the Agile model? How does testing fit in?
Intermediate
▾

Agile is an iterative approach where software is built and tested in short cycles called sprints (1–4 weeks). Testing happens continuously alongside development, not as a separate phase.

Testers collaborate daily with developers and product owners
Test cases are written from user stories in the same sprint
Regression suite grows sprint by sprint
Continuous feedback and fast bug fixes are core to the process
💡 Sprint Workflow
Sprint Planning → Development + Testing in parallel → Bug fixes → Sprint Review → Retrospective → Repeat
Q04
What is the V-Model in testing?
Intermediate
▾

The V-Model (Validation & Verification model) pairs each development phase with a corresponding testing phase. Development flows down the left side of the V; testing flows up the right side.

💡 V-Model Structure
Requirements Analysis ←→ Acceptance Testing (UAT)
System Design ←→ System Testing
Architecture Design ←→ Integration Testing
Module Design ←→ Unit Testing
↓ CODING ↑
Test planning begins at the same time as development — not after
Every development phase has a corresponding test phase
Great for projects where requirements are well-defined upfront
Q05
Explain each phase of STLC in detail.
Intermediate
▾
1. Requirement Analysis: Testers study requirements, identify testable items, and raise queries for ambiguities.
2. Test Planning: Test Lead creates the Test Plan: scope, tools, team, timelines, risks.
3. Test Case Development: Testers write detailed test cases and prepare test data.
4. Test Environment Setup: Configure servers, databases, test tools, and access credentials.
5. Test Execution: Execute test cases, log results, raise bugs, and track them to closure.
6. Test Closure: Write test summary report, calculate metrics, archive artifacts, conduct retrospective.
Q06
What is CI/CD and how does testing fit into it?
Intermediate
▾

CI (Continuous Integration) means developers frequently merge code into a shared repository, triggering automated builds and tests. CD (Continuous Delivery/Deployment) automatically delivers tested code to staging or production.

💡 CI/CD Pipeline Example
Developer pushes code → GitHub triggers Jenkins/GitHub Actions → Build runs → Unit tests auto-execute → Integration tests run → If all pass → Auto-deploy to staging → QA tests staging → Approve → Deploy to production
Q07
What is DevOps and what is QA's role in it?
Advanced
▾

DevOps is a culture combining Development and Operations to deliver software faster and more reliably. QA's role evolves from manual gatekeeper to quality engineer embedded in the pipeline.

QA writes automated tests that run in CI/CD pipelines
QA monitors production metrics and logs (shift-right testing)
QA contributes to infrastructure-as-code and environment automation
Focus: Quality is everyone's responsibility, not just QA's

Test Types
All major types of testing explained with examples
Q01
What is Functional vs Non-Functional Testing?
BasicConcept
▾
Functional TestingNon-Functional Testing
Tests WHAT the system doesTests HOW WELL the system does it
Based on requirementsBased on quality attributes
Example: Login, Search, CheckoutExample: Load time, Security, Usability
Types: Unit, Integration, System, UATTypes: Performance, Security, Compatibility
💡 Example
Functional: "Does the search button return results?"
Non-Functional: "Does the search return results in under 2 seconds when 10,000 users search simultaneously?"
Q02
What is Smoke Testing vs Sanity Testing?
Basic
▾
Smoke TestingSanity Testing
"Is the build testable at all?""Does this specific fix work?"
Broad, shallow — covers major featuresNarrow, deep — focuses on changed area
Done first, on every new buildDone after a bug fix or small change
Done by testersDone by testers (sometimes developers)
💡 Example
Smoke: A new build arrives — check that app launches, login works, home page loads. If not → reject the build.

Sanity: Bug fix for "price not displaying" is deployed → test price display thoroughly before full regression.
Q03
What is Regression Testing vs Retesting?
Basic
▾
Regression TestingRetesting
Tests unaffected areas for side effectsTests the exact bug that was fixed
"Did my fix break something else?""Is the reported bug now fixed?"
Uses existing test casesUses the original failed test case
Planned, broad scopeTargeted, narrow scope
💡 Example
Bug: Payment fails for Visa cards. Fix deployed.

Retesting: Try paying with a Visa card → confirm it now works.
Regression: Also test Mastercard, PayPal, debit cards, refunds — ensure the fix didn't break anything else.
Q04
What is UAT (User Acceptance Testing)?
Basic
▾

UAT is the final phase of testing where actual end users or business stakeholders validate the software against real-world business scenarios before go-live. It answers: "Does this meet our business needs?"

Done by business users, not QA engineers
Uses real or realistic business data
Tests end-to-end business workflows, not individual features
Sign-off from UAT = green light for production deployment
💡 Example
For a payroll system, the HR manager runs UAT by processing the actual monthly payroll for a sample of employees — verifying tax calculations, deductions, and payslips are correct.
Q05
What is Performance Testing? Explain Load, Stress, and Spike Testing.
Intermediate
▾

Performance Testing evaluates how a system behaves under expected and unexpected loads. Common tools: JMeter, k6, Gatling.

Load Testing: Test at expected user volumes. "Can we handle 1,000 users?"
Stress Testing: Push beyond limits to find breaking point. "At what point does the system crash?"
Spike Testing: Sudden, sharp increase in load. "What happens during a flash sale or viral traffic?"
Soak Testing: Sustained load over a long period. "Does memory leak after 72 hours?"
Q06
What is Security Testing? What common vulnerabilities do you test for?
Advanced
▾

Security Testing identifies vulnerabilities that could allow unauthorized access, data theft, or system compromise. It ensures the system is protected from threats.

SQL Injection: Entering SQL code in input fields to manipulate databases. ' OR 1=1--
XSS (Cross-Site Scripting): Injecting malicious scripts into web pages viewed by others
Authentication bypass: Accessing protected pages without proper login
CSRF: Tricking users into performing unintended actions
Sensitive data exposure: Passwords/cards stored in plain text
💡 Tool Examples
OWASP ZAP, Burp Suite, Nessus — used for penetration testing and vulnerability scanning
Q07
What is Exploratory Testing?
Intermediate
▾

Exploratory Testing is simultaneous learning, test design, and test execution without predefined test cases. The tester explores the application using experience, intuition, and curiosity to find unexpected bugs.

Unscripted — no formal test cases, tester decides what to test in the moment
Best for: new features, usability issues, edge cases
Time-boxed sessions (e.g., 60–90 min) called "charters" keep it focused
Finds bugs that scripted testing misses due to rigid test case design
💡 Charter Example
"Explore the user registration flow with the goal of finding data validation issues — spend 60 minutes, try unusual inputs, edge cases, and unexpected navigation paths."

Q09
What is Compatibility / Cross-Browser Testing?
Basic
▾

Compatibility Testing verifies that software works correctly across different environments, devices, browsers, and OS versions.

Cross-browser: Test in Chrome, Firefox, Safari, Edge
Cross-device: Desktop, tablet, mobile (iOS and Android)
Cross-OS: Windows 10/11, macOS, Linux
Tools: BrowserStack, LambdaTest, Sauce Labs
Q10
Explain the 4 Levels of Testing (Unit → Integration → System → Acceptance)
BasicConcept
▾
Unit Testing: Test individual functions/methods in isolation. Done by developers. E.g., testing a single calculateTax() function.
Integration Testing: Test how modules work together. E.g., does the login module correctly pass the user ID to the dashboard module?
System Testing: Test the entire application end-to-end as a whole system against all requirements.
Acceptance Testing (UAT): Business users validate the software meets real-world business needs before go-live.
💡 Analogy
Building a car: Unit = test each engine part. Integration = test engine + transmission together. System = test the whole car. Acceptance = customer takes it for a test drive.

Test Design Techniques
How to design effective test cases systematically
Q01
What is Equivalence Partitioning? How is it used?
Intermediate
▾

Equivalence Partitioning divides input data into partitions where all values in a partition are expected to behave the same way. You test one value from each partition instead of testing every possible value — reducing test cases while maintaining coverage.

💡 Example — Age field (valid: 18–60)
Invalid partition 1: Below 18 → test with 15
Valid partition: 18–60 → test with 35
Invalid partition 2: Above 60 → test with 65

Instead of testing all 60+ valid ages, you test just 3 representative values.
Q02
What is Boundary Value Analysis (BVA)?
Intermediate
▾

BVA tests values at the edges (boundaries) of equivalence partitions because defects are most likely to occur at the boundaries, not in the middle. Test at: minimum, minimum+1, maximum-1, maximum, and just outside.

💡 Example — Password length (6–12 characters)
5 chars → Invalid (below min) ❌
6 chars → Valid (minimum) ✅
7 chars → Valid (min+1) ✅
11 chars → Valid (max-1) ✅
12 chars → Valid (maximum) ✅
13 chars → Invalid (above max) ❌
Q03
What is Decision Table Testing?
Intermediate
▾

Decision Table Testing is used when system behavior depends on multiple conditions simultaneously. A table maps all combinations of conditions to their expected outcomes.

💡 Example — Discount logic
Member + Coupon → 30% off
Member + No Coupon → 10% off
Not Member + Coupon → 20% off
Not Member + No Coupon → No discount

Each row is a test case. All logical combinations are covered.
Q04
What is State Transition Testing?
Intermediate
▾

State Transition Testing tests how the system transitions between different states in response to events. Ideal for systems with defined states and workflows.

💡 Example — ATM login
State: IDLE → Insert card → CARD_INSERTED
Enter correct PIN → AUTHENTICATED
Enter wrong PIN (3x) → CARD_BLOCKED
Enter correct PIN after block → Still BLOCKED (test this!)

Test cases cover each valid transition AND invalid transitions.
Q05
What is Pairwise (All-Pairs) Testing?
Advanced
▾

Pairwise Testing ensures every possible pair of parameter values is tested at least once. Research shows most bugs are caused by interactions between 2 parameters — making pairwise testing very efficient.

💡 Example
Parameters: Browser (Chrome, Firefox), OS (Win, Mac), Language (EN, FR)
Full combinations: 2×2×2 = 8 tests
Pairwise covers all pairs with only 4 tests — 50% reduction, near-same coverage.

Tool: PICT by Microsoft generates pairwise test cases automatically.
Q06
What is Black Box vs White Box vs Grey Box Testing?
BasicConcept
▾

Q07
What is Error Guessing?
Intermediate
▾

Error Guessing is a technique where testers use their experience and intuition to anticipate where defects are likely to occur — and write test cases specifically targeting those areas. It's informal but highly effective.

Leave required fields blank — what happens?
Enter 0, negative numbers, or extremely large values
Enter special characters: !@#$%^&*, emojis, SQL, HTML
Double-click submit buttons, refresh mid-transaction
Paste extremely long text into short input fields
Q08
What is Use Case Testing?
Basic
▾

Use Case Testing derives test cases directly from use cases — the documented interactions between a user and the system. It ensures the system supports real user workflows end-to-end.

💡 Example — "Place an Order" Use Case
Main flow (happy path): Browse → Add to cart → Checkout → Pay → Confirm
Alternate flow: Item out of stock → Suggest similar
Exception flow: Payment declined → Show error, keep cart intact

Defects & Bug Management
How to find, report, track, and manage bugs professionally
Q01
What is the difference between a Defect, Bug, Error, and Failure?
BasicConcept
▾
Error: A human mistake made by a developer while writing code. (Source: the human)
Defect/Bug: The error introduced into the code. (Source: the code)
Failure: When the defect causes the system to behave incorrectly at runtime. (Source: execution)
💡 Example
Developer types price * 1.1 instead of price * 0.9 for a 10% discount. This error creates a defect in the code. When a user applies a discount coupon and gets charged MORE instead of less, that's a failure.
Q02
What is the Defect Life Cycle (Bug Life Cycle)?
Basic
▾

The Defect Life Cycle is the series of stages a bug goes through from discovery to closure.

💡 Bug States Flow
New → Tester logs bug
Assigned → Bug manager assigns to developer
Open → Developer starts working on it
Fixed → Developer fixes and marks as fixed
Retest → Tester retests the fix
Closed → Fix verified ✅ OR
Reopened → Fix didn't work, cycle restarts 🔄
Deferred → Valid bug, fixed in a later release
Rejected → Not a bug (as per design / duplicate)
Q03
How do you write a good Bug Report?
Basic
▾

A good bug report allows a developer to reproduce, understand, and fix the issue without needing to ask the tester questions.

Title: Clear, specific summary. "Login fails with valid credentials on Firefox v120" not "Login broken"
Environment: OS, browser, app version, test data used
Steps to Reproduce: Numbered, exact steps anyone can follow
Expected Result: What should have happened
Actual Result: What actually happened
Severity & Priority: How bad is it? How urgently must it be fixed?
Attachments: Screenshots, screen recordings, logs
Q04
What is Severity vs Priority in bug reporting?
Basic
▾

Severity = technical impact on the system. Priority = business urgency — how quickly must it be fixed?

ScenarioSeverityPriority
App crashes on checkoutCriticalHigh
CEO's name misspelled on About pageLowHigh
Memory leak after 12 hours (rare)HighLow
Tooltip text slightly misalignedLowLow

What tools are used for Bug Tracking / Test Management?

Q06
What do you do if a developer says "That's not a bug, it's a feature"?
Intermediate
▾

This is a behavioral question testing your communication and conflict resolution skills. Never argue emotionally — let the requirements speak.

Reference the requirements document — show what was specified
If requirements are ambiguous, escalate to the Product Owner/BA for clarification
If no written requirement exists, discuss expected user experience
Document the discussion outcome regardless of the decision
Stay professional — the goal is quality, not winning arguments
Q07
What is a Showstopper bug and what action do you take?
Intermediate
▾

A showstopper (blocker) is a critical defect that completely prevents testing from continuing or makes a core feature unusable. It must be fixed before testing can proceed.

Immediately log the bug with Critical severity and High priority
Notify the dev lead and test manager right away (don't just log it silently)
Document exactly which test cases are blocked
Move to test other unblocked areas while the fix is being applied

Test Automation
Automation frameworks, tools, and best practices
Q01
What is Test Automation? When should you automate vs test manually?
Basic
▾

Test Automation uses code and tools to execute test cases automatically, replacing manual repetitive testing. Not everything should be automated.

✅ Automate: Regression tests, smoke tests, repetitive data-driven tests, performance tests
✅ Automate: Stable features that won't change frequently
❌ Don't automate: Exploratory, one-time tests, frequently-changing UI
❌ Don't automate: Usability testing, UX judgment calls
💡 Rule of Thumb
If a test will be run 10+ times and takes 10+ minutes manually, automate it. The break-even point is usually within the first few sprints.
Q02
What is Selenium WebDriver? How does it work?
Intermediate
▾

Selenium WebDriver is an open-source framework for automating web browser interactions. It directly communicates with browsers using their native support, simulating real user actions.

Supports: Chrome, Firefox, Safari, Edge
Languages: Java, Python, C#, JavaScript, Ruby
Locators: id, name, XPath, CSS Selector, className
💡 Basic Python Example
driver = webdriver.Chrome()
driver.get("https://example.com/login")
driver.find_element(By.ID, "username").send_keys("admin")
driver.find_element(By.ID, "password").send_keys("pass123")
driver.find_element(By.ID, "loginBtn").click()
assert "Dashboard" in driver.title
Q03
What is the Page Object Model (POM)? Why is it used?
Advanced
▾

POM is a design pattern where each web page in the application gets its own class containing all its UI elements (locators) and actions (methods). Tests interact with these page classes, not raw locators.

Separates test logic from UI locators — if a locator changes, update one class, not 50 tests
Makes tests more readable: loginPage.enterEmail("user@test.com")
Promotes code reuse — the same page object used in multiple tests
Easier to maintain as the application evolves
💡 Structure
LoginPage.py → stores locators + login(), enterEmail(), enterPassword()
test_login.py → imports LoginPage and calls its methods

When the username field ID changes from user to email, you fix it only in LoginPage.py.
Q04
What are the types of Automation Frameworks?
Advanced
▾
Linear/Record & Playback: Record actions, play back. Simple but brittle. (e.g., Selenium IDE)
Data-Driven: Test logic is fixed; test data comes from external files (Excel, CSV). Run same test with 100 data sets.
Keyword-Driven: Actions described as keywords (CLICK, TYPE, VERIFY) in a table. Non-coders can write tests.
Hybrid: Combination of Data-Driven + Keyword-Driven. Most common in enterprise.
BDD (Behavior-Driven): Tests written in plain English (Gherkin). Tools: Cucumber, Behave, SpecFlow.
Q05
What is BDD and how does Cucumber work?
Intermediate
▾

BDD (Behavior-Driven Development) writes tests as human-readable scenarios using Gherkin syntax (Given/When/Then). Cucumber maps these scenarios to actual code.

💡 Gherkin Example — login.feature
Feature: User Login

Scenario: Successful login with valid credentials
  Given I am on the login page
  When I enter email "user@test.com" and password "Pass@123"
  And I click the Login button
  Then I should see the Dashboard page

Business analysts can write these. Developers implement the step definitions in Java/Python.

▾

Q07
What is the Test Automation Pyramid?
Intermediate
▾

The Automation Pyramid (Mike Cohn) guides how to balance automation investment across levels: more at the bottom (fast, cheap), less at the top (slow, expensive).

💡 Pyramid Levels
🔺 Top — E2E/UI Tests (10%) — Slow, brittle, expensive. Test core user journeys only.
🔷 Middle — Integration Tests (20%) — APIs, services, module interactions.
🟩 Base — Unit Tests (70%) — Fast, cheap, hundreds of tests. Strong foundation.
An "ice cream cone" (top-heavy) anti-pattern: too many UI tests, not enough unit tests = slow, flaky pipeline
Q08
What are Flaky Tests and how do you handle them?
Advanced
▾

Flaky tests pass sometimes and fail sometimes without code changes — they erode trust in automation.

Cause 1 — Race conditions: Use explicit waits (WebDriverWait) not sleep()
Cause 2 — Shared test data: Use isolated, independent test data per test
Cause 3 — Environment issues: Run in stable, dedicated test environments
Cause 4 — Order dependency: Each test should be independent — use setup/teardown
Track flakiness rate — quarantine persistently flaky tests and fix before re-adding

Agile & Scrum
Testing in Agile environments — roles, ceremonies, practices
Q01
What is a User Story and how do you write test cases from it?
Intermediate
▾

A User Story describes a feature from the user's perspective: "As a [role], I want [feature], so that [benefit]." Test cases come from the Acceptance Criteria attached to each story.

💡 Example
User Story: "As a shopper, I want to filter products by price range, so that I can find items within my budget."

Acceptance Criteria:
- Filter shows min/max price sliders
- Products update in real-time as slider moves
- Filter persists when navigating back

Each acceptance criterion → 1+ test cases
Q02
What is the Definition of Done (DoD)?
Basic
▾

The DoD is a shared team agreement on what criteria must be met for a user story or feature to be considered "done." It prevents half-finished work from being marked complete.

Code written and peer-reviewed
Unit tests written and passing
All acceptance criteria tested and passed
No critical/high bugs open
Regression suite updated and passing
Product Owner has signed off
Q03
What are Scrum Ceremonies and QA's role in each?
Intermediate
▾
Sprint Planning: QA reviews stories, identifies ambiguities in acceptance criteria, estimates testing effort
Daily Standup: QA shares: what was tested yesterday, what's being tested today, any blockers
Sprint Review: QA demos tested features to stakeholders, confirms acceptance criteria passed
Retrospective: QA shares what went well/poorly with testing process and suggests improvements
Backlog Refinement: QA reviews upcoming stories early — identifies testability issues before the sprint starts
Q04
What is TDD (Test-Driven Development)?
Advanced
▾

TDD is a development practice where tests are written before code. The cycle: write a failing test → write minimal code to make it pass → refactor.

💡 Red-Green-Refactor Cycle
🔴 Red: Write a test for calculateDiscount(100, 10%) → returns 90. Test fails (code doesn't exist).
🟢 Green: Write the minimal calculateDiscount() function to make the test pass.
🔵 Refactor: Clean up the code — tests still pass, quality improves.

Result: Every line of code has a test. Design is naturally testable.
Q05
How do you estimate testing effort in Agile?
Intermediate
▾

In Agile, estimation is collaborative and relative — using story points or T-shirt sizing rather than hours.

Story Points: Relative effort scale (1, 2, 3, 5, 8, 13...) — complexity, not time
Planning Poker: Team votes simultaneously to prevent anchoring bias
QA factors in: number of test cases, complexity of integration, regression scope, automation time
Track velocity over sprints to improve future estimates

What QA Metrics do you track to measure quality?
Advanced
▾
Defect Density: Number of bugs per module or feature — identifies risky areas
Defect Escape Rate: % of bugs found in production vs. testing — measures QA effectiveness
Test Pass Rate: % of test cases passing per sprint

What is API Testing and why is it important for QA?
Basic
▾

API Testing validates that APIs (Application Programming Interfaces) return correct data, handle errors properly, and perform well — without going through the UI. It sits in the middle of the automation pyramid.

Faster than UI testing — no browser rendering needed

Q04
How do you test a REST API using Postman?
Intermediate
▾
1. Create request: Select method (GET/POST), enter endpoint URL
2. Add headers: Content-Type: application/json, Authorization token
3. Add request body: JSON payload for POST/PUT requests
4. Send request: Click Send and inspect response
5. Write assertions: In Tests tab, validate status code, response body, headers
💡 Postman Test Script
pm.test("Status is 200", () => {
  pm.response.to.have.status(200);
});
pm.test("User ID present", () => {
  const body = pm.response.json();
  pm.expect(body).to.have.property("id");
});
Q05
What do you check when testing an API endpoint?
Intermediate
▾
Status code: Is it returning 200, 201, 400, 404 as expected?
Response body: Are all fields present with correct data types and values?
Response time: Is it responding within SLA (e.g. under 500ms)?
Headers: Content-Type, CORS, Cache-Control correct?
Error handling: What happens with invalid input, missing fields, wrong data types?
Authentication: Does it reject requests without valid tokens?
Data persistence: Does POST actually save data? Does DELETE actually remove it?
